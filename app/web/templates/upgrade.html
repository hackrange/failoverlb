Which modules your nginx was built with, and whether every node agrees.

Why the fleet has to agree

Every node runs the same config, because that is the whole point of a cluster. So a setting is only offered if every node can handle it. One box missing a module means that module's settings disappear from the GUI entirely, for everybody. That is deliberate. The alternative is a change that passes on three nodes, fails its config test on the fourth, and therefore never goes out at all, with nothing obviously wrong to look at.

Adding a module

Modules are compiled in, so there is no installing one at runtime. Add it to the list at the top of nginx-installer.sh on every node, then rebuild from this page. The new settings appear on their own once every node has it.

What actually happens when you press the button.

One node at a time, in order

Standbys first, the active node last. A build takes ten to twenty minutes and ends with nginx restarting, so doing them all at once would mean every load balancer you own is rebuilding simultaneously. Walking them keeps the fleet serving. The active node goes last because it is the one taking config changes, so it is the one worth keeping working while the others are busy.

Every node gets checked before we move on

After each build: is nginx running, does its config still pass, and did the version actually change. Only then does the next node start. Anything that fails stops the walk and leaves the remaining nodes alone. A fleet that is half upgraded is a perfectly good state to be in while you work out what went wrong. A fleet where we carried on and broke the rest the same way is not.

If a build goes bad

The installer takes a snapshot of the binary and the config before every build, so there is always a way back. Use Revert on the node, which runs that same script's revert path and restarts nginx on the old build.

One thing to know about the perl module

If your build includes the perl module, its shared library lives under /etc/nginx/perl and is compiled against one exact nginx version. A binary from a different version refuses to load it, with "undefined symbol", and nginx will not start at all. The installer replaces both together so a normal build is fine. Where it bites is putting an old binary back beside a new library, or restoring /etc/nginx from a backup taken at a different version. The check after each build runs nginx -t, which catches exactly this, which is why the walk stops rather than moving on.

Mixed versions are fine, for a while

Nothing breaks while some nodes are newer than others. The manager works out which settings are safe from the oldest node in the fleet, so it will not offer a directive your laggard cannot parse. You will see fewer settings until the walk finishes, which is the honest answer rather than a broken one.
