      Watching this site's login

      Two shapes, and the second is the reason this exists. Brute force is one address trying many times, which every lockout ever written already stops. Password spraying is one password tried once against a hundred accounts from a hundred addresses: each account sees a single failure so no lockout fires, and each address makes a handful of requests so no rate limit fires. It is invisible to both of the defences you already have.

      This reads the access log, so it sees the address, the path and the status and never a username or a password. It cannot tell you which accounts were targeted, only that the shape is there. Seeing usernames would mean reading request bodies, which is where the passwords are.

      One per line. A path matches itself and anything under it, and * works the same way it does in a WAF exclusion.
      Comma separated.
      Per application, and there is no universal answer. A form that re-renders with "wrong password" answers 200 and answers 302 when it worked, so for that one 200 is the failure. An API answers 401. Get this wrong in the other direction and every successful login is reported as an attack.
      How far back a burst is measured over.

      When to call it

      All three spray rules have to hold at once, because any one alone is an ordinary Monday morning: a busy login page has plenty of failures, a big office has plenty of addresses, and everybody typing their password wrong once is exactly "few per address". It is the combination that does not happen by accident.

      The slow window runs the same test over hours instead of minutes, because somebody who knows detectors use five minute windows waits six.

      Worth knowing

      With no certificate attached, the https server block is left out altogether. That is on purpose: nginx refuses to start at all if it finds an ssl listener with no certificate, so writing one anyway would take the whole box down rather than just this site.

      Handles any request whose Host header does not match another site.

      Why you want one

      Without a default, nginx uses whichever server block it loaded first, which is usually not what you meant and moves around as you add sites. People find your server by IP address and get a random one of your sites. A default that returns a plain 404 keeps that tidy.

      Terminate TLS here, hold the certificate here, and pass everything else through untouched.

      What it stops doing

      Normally a site is assumed to be yours, so it gets a set of security headers whether or not the application behind it sent its own: HSTS, X-Frame-Options, X-Content-Type-Options and a Referrer-Policy. Each one is written by hiding the backend's copy first, because two copies that disagree is worse than either alone. That is right for a site you own and wrong for one you are only carrying traffic for, where the application's own Content-Security-Policy is the one that has been tested.

      With this on, none of those are written and none of the backend's are hidden. Neither are the redirect and cookie rewrites, the response text replacement, the custom response headers, or this site's own Server header handling. Serving a whole website under a path is off too, since a mount is nothing but rewriting.

      The one it cannot undo

      The Server header. The installer writes more_set_headers "Server: server" into nginx.conf for the whole box, so every response says that whatever any one site asks for, and nginx replaces an upstream's Server and Date headers with its own before any site setting is read. A site cannot override a decision made for the box. If the application's own Server header has to reach the browser, that line comes out of nginx.conf, which is a change to every site on the node rather than to this one.

      What it still does

      Host, X-Real-IP and the four X-Forwarded headers, which are how the backend learns who asked and that the request arrived over https. SNI to the backend, and a backend path if the pool has one, because those are how the request reaches the application at all rather than rewrites of anything.

      A pool token is left alone as well. That one is this load balancer proving itself to the backend, not a rewrite of something the backend sent, and dropping it from here would either break a backend that checks it or quietly remove the check. The WAF, CORS, geo blocking and the access list are untouched too: they decide who gets through rather than what their headers say, and each has a tab of its own.

      Turning it off

      Gives the site back exactly the settings it had. Nothing is cleared, the renderer simply stops reading them while the mode is on, so this is safe to try on a site that is already configured.

      Locks this site to the management networks and the cluster nodes.

      What it writes

      An allow line for every node in the cluster plus your management networks, then deny all. The node list is generated from the roster, so a node you add later lands in here on its own.

      Two ways to drive a site, and you can switch between them.

      Generated, the normal way

      The config comes from the settings on the other tabs. Every value is checked before it is stored, the help explains what each one does, and settings your nginx cannot run are not offered. The config here is read only so you can see exactly what your choices produced.

      Hand written

      You write the whole server block. Useful for something the forms do not cover yet, or config you already have and want to bring across as is. The forms stop driving this site while it is in this mode, so the two cannot fight over the same file.

      You still cannot break the fleet

      Hand written config goes through exactly the same checks as everything else. It is tested by nginx here before it is even saved, and at apply time every node stages it and runs nginx -t before any node goes live. If one node says no, nothing changes anywhere. So the worst case is a config that refuses to save, not a fleet that stops serving.
