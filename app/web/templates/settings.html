Certificates

Where the certificate authority sends expiry warnings. Leave it empty and certificates still work, you just do not get that mail. The dashboard warns you either way. Use a list more than one person reads, not somebody's personal mailbox.
Staging certificates are not trusted by browsers, but the rate limits are far looser. Leave this on while you are working things out.
Lets Encrypt certificates last 90 days and they suggest renewing at 30. That leaves a fortnight to notice a failure and still have time to fix it.

Buying from a named authority

Certificates you pay for come from an authority you set up on its own page, so you can use more than one and so Lets Encrypt keeps working alongside them. See Paid Certificate Authorities.

DNS

One per line. Leave it empty to use 1.1.1.1, 8.8.8.8 and 9.9.9.9. These decide which node gets to ask for a certificate, so they should see the same answer the certificate authority will.
Worth having on a split horizon network, where the internal answer is the one that matters. Answers from every server are merged, so a resolver that disagrees adds a possibility rather than overriding anything.

Management networks

One CIDR per line. These get an allow line on any site set to management only, along with every cluster node.
This is not the same thing as who can reach this GUI. That is NFM_ADMIN_ALLOWLIST in the environment, because it has to be in force before the login page will even render, which is earlier than anything in the database can be read.

Country database

Needed before a site can block anywhere. It is a file next to nginx on every node, and a node without it refuses the whole config, so this puts it on all of them and keeps it current.

db-ip publish a country database every month and ask for nothing but attribution. Pick MaxMind if you already have an account or want theirs.
Stored encrypted and never sent back to this page. Leave it blank to keep the one already saved.
Both sources publish monthly, so monthly is plenty. Daily costs a download and finds nothing new most days. The active node does it, for the whole fleet.
Save the page first, then install: the download uses whatever source is saved here. db-ip's free database is licensed CC BY, so if you publish anything derived from it, credit them.

Firewall rule set

checking the fleet

The OWASP Core Rule Set, which is what the firewall actually checks requests against. Same story as the country database: it is files next to nginx on every node, and a node without them refuses the whole config, so this puts them on all of them and keeps them current.

The long term support line gets fixes and few new rules, which means few new false positives. Latest catches more, and the price is that a new rule can start refusing something your own application does, on a site already in blocking mode.
Monthly suits the support line. Whatever you pick, the active node does it for the whole fleet, and the rules are swapped in one step so nginx never reads half of one version and half of another.
Save the page first, then install: the download follows whichever track is saved here. Having the rules on a node does not switch anything on. A site only gets checked once its own firewall setting is turned on, and that starts in watching mode.

How the manager talks to the certificate authority.

The email really is optional

Lets Encrypt will issue certificates with no contact address at all. The only thing you give up is the mail they send when something is about to expire. That matters less here than it would somewhere else, because the manager is already watching expiry and puts a warning on the dashboard weeks ahead. Set one anyway if you have a shared mailbox, since a second warning path costs nothing. Just do not use somebody's personal address, because certificates outlive jobs.

Renewal is driven from here, not by certbot

The certbot timer is turned off on purpose. It fires on every box, and on a node that does not currently own the public address the challenge fails every single time. You end up with a mailbox full of failures from two of your three nodes and the real problem buried in it. The manager works out which node can actually answer, at renewal time, with current DNS, and runs it there.

Lets Encrypt runs a practice service alongside the real one.

Why you want it on at first

The real service has hard rate limits: five certificates a week for the same set of names. Get your setup wrong a few times and you are locked out for a week, with no way to appeal. Staging has far looser limits. The certificates it issues are not trusted by browsers, so you will see a warning, but everything else behaves the same. Get it working there, then turn this off and do it for real.

Switching to real certificates

Turn this off and issue again. The staging certificate gets replaced. Nothing else needs changing.

Which DNS servers the manager asks when it needs to know where a domain points.

What this decides

Before asking for a certificate, the manager looks the domain up and compares the answer against what each node reports its own public address to be. Whichever node matches is the one that runs certbot, because it is the only one the certificate authority will actually reach. Ask the wrong resolver and you get the wrong answer, and the job goes to a node that cannot possibly answer the challenge.

Why the default is public resolvers

An internal resolver very often has a split horizon answer, pointing at a private address for a name that is public. That is useful for your own traffic and actively wrong here, because the certificate authority is out on the internet and will see the public answer. If your boxes cannot reach 1.1.1.1 and friends, put your own resolvers here. Just make sure they give the public answer for names you want certificates for.

Not the same as nginx's resolver

This is the manager deciding which node should ask for a certificate. nginx has its own separate resolver setting, for looking up backend hostnames while it is running, and that is per site under Advanced. They are unrelated and you may well want different values in each.

Networks that count as yours when a site is set to management only.

What it does

Any site with "management network only" ticked gets an allow line for each of these, plus one for every node in the cluster, then a deny all. The cluster nodes are added from the roster rather than typed in, so when you add a node later it lands in every one of those lists on its own. That is the bit people forget by hand, and it is how health checks end up blocked by an ACL somebody wrote months earlier.

Not the same as the GUI allow list

This decides who your nginx sites let in. Who can reach this management GUI is a separate setting in the environment, and it has to be, because it is enforced before the login page renders and therefore before anything in the database has been read.
