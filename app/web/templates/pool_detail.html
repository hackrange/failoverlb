How nginx decides which backend gets each request.

What is available

  • Round robin takes turns. Right when your backends are much the same.
  • Least connections picks whoever has fewest open. Better when requests take very different amounts of time, because a slow backend piles up connections and naturally stops being chosen.
  • Pin by client address sends a given IP to the same backend. Careful: a whole office behind one NAT address all lands on one server.
  • Pin by a value is the same idea on anything you name, usually a cookie. Nearly always better than pinning on the address.
  • Random two, least connections picks two at random and takes the quieter. Good on big pools, where plain least connections makes everything pile onto whichever server just freed up.

Not here

least_time is paid only. Least connections tracks it closely in practice, and the adaptive weighting on the last tab gets you the rest of the way.

Changes what happens to everybody else when one backend goes away.

Why it matters

Without it, removing one backend from a pool of four reshuffles roughly everybody, because the hash is taken modulo the number of servers and that number just changed. Every user lands somewhere new and, if you are relying on stickiness, every session breaks at once. With it, only the users who were on the server that went away move. Everybody else stays exactly where they were.

How many idle connections to each backend nginx holds open for reuse.

Worth having

Without it every single request opens a fresh TCP connection, and over TLS pays for a full handshake too. On a busy site that is a lot of work for nothing.

The catch

It only does anything if the proxy is speaking HTTP/1.1 and the Connection header is cleared. The manager writes both of those for you, so setting a number here is enough.

A floor on how far the health checker is allowed to take the pool down.

What it protects against

If applying the failures would leave fewer than this many backends up, the manager leaves them all in instead and logs loudly. A pool serving errors is bad. A pool serving nothing at all, because a switch rebooted and every check failed in the same second, is worse. That failure mode is avoidable so we avoid it.

Two different things watch your backends.

nginx does passive checks

It notices when a real request fails and stops using that backend for a while. That is the Fails and Timeout columns on the backends tab. It is all the free nginx has on its own, and the catch is that a user had to get an error first.

The manager does active checks

It reaches out on a schedule whether or not anybody is browsing. When a backend fails enough times in a row the upstream is rewritten with that server marked down and nginx reloads. So it is out of rotation before a user finds it. Every node checks separately and the results are kept apart, so a backend one load balancer can reach and another cannot shows up as exactly that, which is usually the whole answer.

Picking the numbers

Down after 3 at a 5 second interval means a dead backend is out within about 15 seconds. Lower is twitchier and reacts to a single dropped packet. Higher is calmer and slower.

What to put in the Host header when checking.

When you need it

If the backend serves several sites by name, a request with no Host, or the wrong one, gets the default site or a 404. The check then reports the backend as down when it is perfectly healthy, and you spend an hour looking at the wrong thing.

Keeps a user on the same backend, which apps holding session state in local memory need.

How this is done here

The paid nginx has a sticky cookie feature. The free one does not, but it can hash on anything, so the manager writes the cookie half: a map that reads a route cookie, a header that sets it when the client has none, and an upstream hashing on it with consistent turned on. Same result, put together from parts that are in the free build.

Worth saying

The real fix is not needing it. Put sessions in redis or the database and any backend can serve any user, so you can take a server out whenever you like. Sticky sessions are a workaround, and they come with a cost: when a backend dies, everybody on it is logged out.

Eases traffic back onto a backend that just came back, rather than all at once.

Why

A JVM app that just restarted has a cold JIT, an empty connection pool and no warm cache. Give it a third of your traffic the instant it passes one health check and it can fall straight back over. Then it recovers, gets slammed again, and flaps. That is worse than it having stayed down.

How it works here

The manager ramps the weight in a handful of steps across your window. Not as smooth as doing it inside nginx, since each step is a config reload, but the point is simply to not hit a cold server with everything at once, and steps do that fine.

Leans traffic toward whichever backends are answering fastest.

Where the numbers come from

The health checker is already timing every check, so it knows which backends are slow. This turns that into weights.

The rails on it

Weights move one step at a time between a floor and a ceiling, so one slow check cannot pull a server out of rotation. And if everything is slow, nothing changes, because that means the problem is downstream and shuffling weights would just pile load onto whichever box is least broken.

Honest comparison

The paid least_time reacts per request. This reacts on a cycle, so minutes not milliseconds. Good for backends that are consistently different speeds, like mixed hardware. For traffic that spikes in seconds, plain least connections reacts faster and you should just use that.
